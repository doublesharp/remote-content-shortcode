# Security and compatibility

Remote Content Shortcode fetches content when a post or page is rendered. Any visitor who can view that post can view its imported content. A credential used for fetching does not restrict who can read the resulting page.

## Request destinations

Only absolute public HTTP and HTTPS URLs are accepted. Local files, non-HTTP schemes, URL-embedded passwords, loopback addresses, private networks, link-local addresses, shared address space, and other nonglobal addresses are rejected. WordPress's safe HTTP port restrictions also apply.

The destination is normalized using the same URL parser as WordPress Requests. WordPress's safe HTTP validator requires an IPv4 address record; IPv6-only DNS names and literal IPv6 URLs are unsupported. For accepted hosts, all returned IPv4 and IPv6 addresses are checked, and a public IPv4 address is selected and pinned in the cURL transport. The original hostname remains in the Host header and TLS SNI and is used for certificate verification. A hostname cannot pass the public-address check and then resolve to an unchecked private destination during that connection.

The request fails closed if a Requests hook changes its URL or HTTP method. The pin and TLS options are enforced after ordinary cURL hooks, and the peer address is checked after connecting. Successful responses require the protected transport to have run. WordPress pre_http_request integrations may provide an offline response without making a network connection through this plugin.

GET requests can follow up to three redirects. Each destination is normalized, validated, and pinned independently. Authenticated requests and POST requests do not follow redirects. Requests use a shared timeout budget across redirects, from 1 to 30 seconds; system DNS resolution may add time outside that budget.

WordPress proxy routing is refused, and environment proxy settings are disabled for these requests. Private intranet imports and proxy-only outbound networking are not supported. The former URL-bypass constants and SSL-verification filters are not honored.

## HTML and resource limits

The final HTML passes through `wp_kses_post()` after CSS selection, element removal, regular expression replacement, entity encoding, and the return filter. This removes markup WordPress does not permit in post content, including scripts and inline event handlers. There is no shortcode attribute that disables sanitization.

`htmlentities="true"` displays source as escaped text. `strip_tags="true"` returns text and removes script and style content. Remote HTML is never executed as PHP. Optional fallback HTML is limited to 4,096 bytes and sanitized separately when the import fails or produces empty output; it is never evaluated as a shortcode.

Opt-in URL rewriting resolves href, src, poster, cite, and ordinary srcset values against the final redirect destination. It never makes an additional server-side request. Imported base elements cannot change the destination used for resolution. Only HTTP(S) targets and permitted contact links are retained, and the final HTML still passes through KSES. Local fragment anchors are preserved. CSS URLs, form actions, background and longdesc attributes, and ambiguous/data srcset values are not rewritten. URL values containing literal whitespace are dropped rather than guessed. Rewriting is bounded to a 1 MiB input/output and 20,000 markup openings/elements.

The plugin advertises uncompressed responses and rejects Content-Encoding responses before WordPress Requests can decompress them. Responses at or above 1 MiB are rejected. CSS output is limited during accumulation, preventing overlapping selectors from expanding a small document into an unbounded result. Replacement patterns are limited to 1,024 bytes and 32 opening parentheses, replacement strings to 4,096 bytes, and replacements to 1,000 per render. Regex input is limited to 256 KiB to bound capture allocation. Replacement backreferences are expanded incrementally against a 1 MiB output budget, before allocating an oversized result.

Before evaluating any CSS selector, a linear document walk rejects more than 2,000 elements or depth greater than 32. Each selector is limited to 256 bytes and 16 conservatively counted steps, groups, and pseudo-class markers. A combined work budget inspects the generated XPath: simple selections have a linear cost, descendant and ancestor traversal has a quadratic cost, and sibling traversal has a cubic cost in the element count. Depth, selector steps, and grouped results also contribute. This admits ordinary tag and class selections while rejecting expensive combinations below the individual limits. Text-only and entity-encoded responses that do not request CSS processing are not subject to these DOM limits. Output-size limits alone do not bound selector evaluation time.

These are conservative compatibility limits, including for adjacent sibling selectors and pseudo-classes that generate sibling axes. With no removal selector, `main p` at depth 20 is limited to 894 total elements, while `h2 + p` is limited to 200 elements. Counts include parser-created wrappers. Selection and removal share a budget of 32 million work units, so additional expressions reduce the available budget. Use sibling selectors on small fragments; simple tag and class selections can use the full document limit, subject to depth and selector limits.

The cURL transfer-progress callback returns an abort signal when downloaded bytes reach the limit, including unknown-length responses on supported older cURL versions. Declared oversized responses are also rejected using cURL's file-size limit. Requests retains at most 1 MiB of body data. Network requests retain their configured timeout; DNS resolution remains outside a strict application-level deadline.

Invalid input, failed requests, unsuccessful HTTP statuses, unsupported selectors, and invalid regular expressions return empty output. Server-side code can observe the `remote_content_shortcode_error` action. Its URL argument can contain sensitive query values and must be handled accordingly; diagnostic listeners should never print raw error details to visitors.

## Credentials and forwarded data

The `userpwd` attribute selects an administrator-defined alias. It cannot directly name an arbitrary option, constant, or metadata key or contain a plaintext password. Administrators manage encrypted aliases in **Tools → Remote content → Connections**, or configure them in trusted PHP. Each alias grants access to an HTTPS origin, exact normalized endpoint path, and allowed methods. GET is the default permitted method; POST must be granted explicitly. Aliases support Basic authentication by default, Bearer tokens through auth=bearer, or API keys through auth=api_key with a configured header. Header names are limited to X-* or Api-Key; routing, forwarding, proxy, cookie, and method-override names are refused. Credential values are bounded and reject control characters. No authentication type permits redirects or response caching.

Managed connections are limited to 32 per site. Secrets are limited to 8,192 bytes and stored as authenticated encrypted envelopes in a non-autoloaded option. Sodium secretbox is preferred; AES-256-GCM is the fallback. Encryption keys derive from the WordPress salts and a plugin-specific context. No plaintext fallback exists. Salt rotation makes existing sealed secrets unreadable. Keep the salts with database backups and re-enter managed secrets after changing them. Database backups and salts together permit decryption and need appropriate access controls. Connection metadata and forms never display plaintext or encrypted secret values. Blank updates retain the prior secret; explicit removal erases it.

PHP aliases override matching managed aliases and appear as read only. The Connections list shows their names without exposing their storage keys or endpoint scope. Existing constants, external options and protected metadata remain separate credential sources; the connection manager does not rewrite them.

Metadata credentials require an explicit integer post_id and a protected metadata key. Metadata registered for REST exposure is refused. The ambient post or loop never selects a credential source. Constant or option storage is preferred. Configuring an alias grants shortcode authors access to the configured endpoint. Query values can vary, and fetched data is published according to the post's ordinary visibility. Use service credentials intended for publishing this data, preferably read-only credentials. Do not configure aliases for confidential or administrative endpoints.

Only explicitly named query-string values are forwarded through `params`. They are URL-encoded and must be scalar strings. Cookies and incoming POST parameters are excluded. Visitor cookies and inbound Authorization headers are not forwarded. Enclosed shortcode content is sent as the body only for POST.

## Caching

Only unauthenticated GET results for logged-out visitors, including public REST-rendered content are cached. Logged-in requests, editor previews, and administrator diagnostics bypass caching so they cannot evict public visitor entries. The key includes the final URL with forwarded parameters, request configuration, WordPress site, and current WordPress user. Raw successful responses are cached so each render still applies its own selectors, replacements, filters, and final sanitization. Request failures, including DNS validation failures, are cached for up to 60 seconds or the configured cache lifetime if shorter. Cached errors contain only a sanitized error code, with no transport message or data. They return empty output unless fallback content is configured and notify diagnostic listeners. POST, authenticated requests, and requests with cache=false are not cached.

Caching uses an external WordPress object cache when installed, otherwise expiring database transients. A per-site, non-autoloaded metadata option tracks at most 32 entries and 8 MiB of serialized cached payloads. Metadata contains hashed identifiers, expiry times, and byte counts; it contains no raw URLs or credentials. A token-owned option lock serializes cache mutations; lock contention skips a write instead of blocking rendering. A lock abandoned by a terminated process can defer cache writes and clearing for up to 60 seconds. Cache locking uses MySQL/MariaDB semantics; alternative database drop-ins are not qualified. Cache lifetimes range from 1 to 86,400 seconds. Eviction can remove entries earlier.

stale_ttl defaults to zero. When enabled, a cached unauthenticated GET can reuse its last successful raw response for up to 86,400 additional seconds if a refresh fails. Negative cache entries preserve that success without extending its original deadline. POST, authenticated requests, and cache=false cannot use stale content. Stale responses use the same site/user/request identity and rerun transformations and sanitization. Cache keys also include requested fresh and stale lifetimes.

Administrators can invalidate one exact normalized request URL or all plugin entries through Tools > Remote content > Cache. URL matching uses the actual request URL after forwarded parameters and URL filters; the clearing form does not run those transformations again. Both forms require manage_options and a valid nonce. Other caches are untouched. Diagnostic requests use the protected renderer and report only bounded status fields, a sanitized preview, and allowlisted error codes. They do not echo raw transport errors, source URLs, query values, or credentials. Administrator diagnostics bypass caching and cap their timeout at five seconds; they do not measure visitor cache hits. The builder's generated shortcode intentionally contains the public configuration supplied for copying. Shortcode diagnostic actions remain server-side hooks and require the separate precautions described above.

Uninstall removes plugin cache metadata, payloads and managed connection records on each site. It preserves credential constants, external credential options, protected metadata and unrelated cache data. Deactivation preserves the plugin's settings and managed connections.

## Free and extension boundaries

Free includes its shortcode, block, transformations, public GET cache, stale fallback, URL rewriting, Basic/Bearer/API-key connections and administrator tools. It has no licensing client and makes no licensing-service requests. Pro installs separately and uses the shared transport and rendering APIs. Licensing affects Pro updates; installed Pro features do not depend on a remote entitlement check.

`fetch_source()` returns raw verified transport bytes, including JSON or HTML that may be unsafe to publish. `render_fetched()` applies the existing HTML transformation and sanitization pipeline without making a request. Add-ons must validate their own stored data and authorization and must not echo raw response bytes as HTML. Disabling content filters for a stored fetch skips ambient query forwarding and the URL/POST-body content filters; it does not weaken URL, credentials, DNS, TLS, redirect or response limits. See [the extension reference](integrations.md).

## Compatibility

The plugin requires WordPress 6.6, PHP 8.2 or later, DOM, and cURL 7.49 or later with CURLOPT_CONNECT_TO support. CSS selection uses the isolated Symfony CssSelector component with native DOM. Standard CSS selectors and some extensions are supported, including `:contains()`. Compatibility with phpQuery is not complete; jQuery-only selectors such as `:eq()` are unsupported.

The shortcode is registered in frontend, administration, and REST contexts. Rendering it in an editor preview or a REST response can make a remote request, subject to the same restrictions as ordinary post rendering. This differs from version 1.5's frontend-only registration. The dynamic block calls the same renderer and stores only public configuration and credential aliases in post content. Its editor preview uses WordPress's authenticated block-renderer endpoint; diagnostic tools do not create a public request endpoint.

The existing URL, POST-body, pre-selection HTML, and return filters remain available. The `remote_content_shortcode_phpQuery` name remains for compatibility, though phpQuery is no longer included. The SyntaxHighlighter integration processes only `remote_content` shortcodes and sanitizes the resulting HTML.

Version 1.x installations that depend on raw scripts, intranet URLs, compressed responses, proxy routing, implicit credential lookup, unlimited cache lifetimes, or jQuery-only selectors need migration. These behaviors are intentionally restricted in version 2.
